1. THE PROJECT IN SIMPLE WORDS
------------------------------
The user types a task. The program looks at the screen, decides where to
click or what to type, does it, then checks whether it worked.

Research question (suggested wording):
"How much does a lightweight local verifier improve the task success of a
small GUI agent, and what does it cost in time and memory, compared with a
pixel-difference rule and a larger vision-language model?"


2. WORDS YOU MUST KNOW
----------------------
GUI             Graphical user interface: buttons, boxes, menus.
Agent           A program that observes, decides and acts in a loop.
Screen parser   Finds elements in a screenshot.
Bounding box    Rectangle around an element (x1, y1, x2, y2).
OCR             Reads text from an image.
Grounding       Matching words ("the login button") to a place on screen.
Verifier        Decides whether the last action worked.
Baseline        A simple method you compare your method against.
Ablation study  Remove or swap one part and measure what changes.
Fine-tuning     Training an already pretrained model on your own data.
Train/val/test  Data to learn from / to tune with / for final scoring.
Data leakage    Test information getting into training. Makes results invalid.
Ground truth    The correct answer.


3. HOW THE WHOLE SYSTEM WORKS
-----------------------------
 User instruction
        |
    [Planner]  -> list of steps
        |
        v
 +--> [Capture BEFORE screenshot]
 |          |
 |    [Parser + OCR]  -> list of elements (type, box, text)
 |          |
 |    [Grounding]     -> the chosen element
 |          |
 |    [Executor]      -> click / type / scroll / key
 |          |
 |    [Wait until the screen stops changing, with a time limit]
 |          |
 |    [Capture AFTER screenshot]
 |          |
 |    [Verifier]      -> success or failure, with a confidence score
 |      |         |
 |   success    failure -> retry / choose next candidate / replan / stop
 |      |         |
 +------+---------+   until task done, step limit, or stop key

IMPORTANT RULE: while running, the agent sees only pixels (screenshots).
It must not read the page's HTML (DOM). You MAY use the DOM to create
training labels and to score results, because that is the examiner's
answer sheet, not the agent's eyes. State this clearly in the report.


4. ONE FULL EXAMPLE
-------------------
Instruction: Log in with username "testuser" and password "test123"

Planner output:
  1. click  target="username field"
  2. type   text="testuser"
  3. click  target="password field"
  4. type   text="test123"
  5. click  target="login button"
  6. expect "the logged-in page appears"

Step 5:
  - Capture the before screenshot.
  - Parser returns, for example:
      id 1  textbox  [400,300,800,340]  "Username"
      id 2  textbox  [400,360,800,400]  "Password"
      id 3  button   [400,430,520,470]  "Login"
  - Grounding scores each element against "login button" and picks id 3.
  - Executor clicks the centre of the box: (460, 450).
  - Wait, then capture the after screenshot.
  - Verifier gets before, after, action type and click position.
  - It returns, for example, success with 0.94.
  - If failure: follow the retry rules in section 14.

8. PART A: PRACTICE WEBSITES
----------------------------
Make small local sites so tests are safe and repeatable.
Suggested: login, sign-up form, search and results, to-do list, settings
page with checkboxes and dropdowns, simple shop cart, multi-page form.

Vary: colours, fonts, button positions, labels ("Login" / "Sign in"),
page size, light and dark themes.

Build in failures you can switch on:
  - button does nothing
  - slow loading
  - popup covering the target
  - validation error
  - page layout shifts before the click
  - an unrelated thing changes (clock, advert, animation) while the
    action fails
The last one matters: a pixel rule is likely to be fooled by it.

Split the sites NOW: training sites, validation sites, test sites.
Never train on test sites.


9. PART B: SCREEN CAPTURE AND ACTIONS
-------------------------------------
Capture: mss for the screen. Save PNG files.
Actions: click, type, press key, scroll.

Which tool does what:
  PyAutoGUI  = the agent's mouse and keyboard.
  Playwright = open and reset test pages, make labels, check final result.

Coordinate problems to solve early:
  - Windows display scaling (125%, 150%) can shift clicks. Make the program
    DPI-aware or fix scaling at 100%, then test it.
  - Playwright positions are relative to the page, not the whole screen.
    You must add the browser window's offset and account for scaling.
  - Start with one monitor and a fixed browser size.
  - Playwright page screenshots show the page only; mss shows the screen.
    Use the same capture type for training and running.

Test: draw a dot on the screenshot where you plan to click and compare it
with where the click really lands.


10. PART C: PLANNER
-------------------
Your proposal says "change the plan", so something must make plans.
It is not one of your three models.

Suggested for version 1: rule-based. Support a limited set of phrasings
and task types (log in, fill form, search, tick, select). Output steps as:
  {"action": "click", "target": "login button", "text": null,
   "expect": "next page appears"}

State this limit openly. A language-model planner is a possible extension,
but it adds another variable to your experiments.


11. PART D: SCREEN PARSER (ML MODEL 1)
--------------------------------------
Input:  screenshot.
Output: list of {class, box, confidence, text}.

Classes (suggested, keep few): button, textbox, link, checkbox, radio,
dropdown, icon.

Data:
  - Best source: your own pages. Playwright can give element boxes from the
    DOM, so labels are created automatically. Check samples by eye and
    remove hidden or covered elements.
  - Add hand-labelled screens (Label Studio) from other layouts.
  - Rico is mainly mobile. If you use it, test whether it actually helps.
  - Suggested start: a few thousand auto-labelled screenshots with real
    variety. Many near-identical copies add little.

Model: a small pretrained YOLO. Ultralytics uses the AGPL-3.0 licence
(or a paid one): check what that means for your public repo.

Training: fine-tune, use validation data to stop and tune, try image size
carefully because small icons disappear when shrunk. Do not use left-right
flipping, since it mirrors text and layouts.

OCR: run it on the screenshot, then attach text to boxes by overlap and
nearness (a textbox label is often above or left of the box).

Metrics: precision, recall, mAP@0.5, mAP@0.5:0.95, results per class,
time per image.


12. PART E: GROUNDING (ML MODEL 2)
----------------------------------
Input:  target phrase + element list.
Output: ranked list of elements with scores.

Step 1, baseline (no training): fuzzy text match between the phrase and
the OCR text, plus element type.

Step 2, trained model: for each candidate combine
  - text similarity (small sentence-embedding model)
  - element type
  - position and size
  - optionally an image crop (for icons with no text)
and train a small ranking classifier: correct element = 1, others = 0.

Data: (phrase, screenshot, correct element) examples from your pages.
Write many phrasings: "login button", "sign in", "press log in".
Keep some phrasings for testing only. Check Mind2Web's format and licence
before planning to use it. Keep ScreenSpot for testing only.

Metrics: top-1 accuracy, top-3 accuracy, click-inside-correct-box rate.
Test it twice: with ground-truth boxes (grounding alone) and with parser
boxes (real pipeline). This shows which part causes the errors.


13. PART F: VERIFIER (ML MODEL 3, MAIN CONTRIBUTION)
----------------------------------------------------
Input:  before image, after image, action type, click position, and maybe
        the typed text or expected result.
Output: success probability.

Define "success" precisely before collecting data. Suggested: "the
intended effect of this single step happened". Write a rule for each
action type. Examples:
  click login with valid details -> logged-in page shown
  type "testuser"                -> that field now contains it
  click checkbox                 -> that checkbox changed state
  scroll down                    -> content moved down

Note: the model can only judge intent if it is told the intent. Action
type and position alone may not be enough. Test adding the expected result.

The three verifiers to compare (plus no verifier):
 1. Pixel rule: difference between before and after. If the changed share
    is above a threshold, say success. Choose the threshold on VALIDATION
    data only.
 2. Your model.
 3. A small open vision-language model run locally, asked the same
    question with a fixed prompt. Check it fits your laptop. If you run it
    elsewhere, report that hardware, and do not compare speeds as if equal.

Suggested model design:
  - Same pretrained small CNN (e.g. MobileNetV3 or ResNet18) applied to
    before and after (shared weights).
  - Combine: before features, after features, their difference.
  - Add: action type embedding, click position, expected-result embedding.
  - Add: a crop around the click from both images, because small changes
    vanish in a resized full screen.
  - Final small layers -> one number -> sigmoid.
  - Loss: binary cross-entropy, with class weights if unbalanced.
  - First train only the new layers, then unfreeze some CNN layers.

Data collection (automatic):
  1. Reset the page.
  2. Capture before.
  3. Do a correct or deliberately wrong action (miss the button, click a
     neighbour, type in the wrong field, press when disabled).
  4. Wait. Capture after.
  5. Let the DOM check set the label.
  6. Save images and a JSON record: site, action, position, expected,
     label, failure type.
Suggested start: 1,000 examples to test the pipeline, then grow to several
thousand with balanced success/failure. Manually check a random sample.

Split by SITE or template, not by random row. Random splitting puts nearly
identical screens in train and test and inflates the score.

Metrics: precision, recall, F1, confusion matrix, accuracy per failure
type, inference time, memory, model size.
The most dangerous error is saying success when the action failed. Report
that rate separately.

Ablations on your model: without difference features; without click crop;
without action information.


14. PART G: AGENT LOOP, RETRY AND SAFETY
----------------------------------------
Pseudo-code:
  steps = planner.make(instruction)
  for step in steps:
      attempts = 0
      while True:
          check stop key and limits
          before = capture()
          elements = parser(before)
          target = grounding(step, elements, excluding=failed_targets)
          executor.run(step, target)
          wait_until_stable(timeout)
          after = capture()
          if verifier(before, after, step) is success: break
          attempts += 1
          choose recovery, or stop and report failure

Recovery order (suggested):
  1. Wait longer and check again (the page may be slow). Do not repeat the
     action yet.
  2. Retry the same target once.
  3. Try the next-best candidate.
  4. Scroll to look for the target.
  5. Replan, or stop and tell the user.
Careful: repeating an action can toggle a checkbox back or submit twice.
Check the current screen before every retry.

"Task done" must be defined. The agent decides using the screen; your
evaluation script separately checks the truth through the DOM. Count the
cases where the agent claims success but is wrong.

Safety:
  - Maximum steps, maximum retries, time limit.
  - Global stop key (pynput).
  - Keep PyAutoGUI FAILSAFE on (mouse to a screen corner stops it).
  - Allow only your practice sites. Stop if another window takes focus.
  - Fake accounts only.

Logging: for every step save screenshots, elements, chosen target, scores,
action, verifier result, time taken. You will need this for error analysis.


15. PART H: USER INTERFACE
--------------------------
Simple desktop app (Tkinter is built in; PySide6 looks better).
Needs: instruction box, Start, Stop, current step, log, last screenshot,
verifier result, final success or failure message.
Run the agent in a separate thread so the window does not freeze.

For privacy: after downloading models, disconnect the internet and show it

16. EVALUATION AND EXPERIMENTS
------------------------------
Task list: suggested 30 to 50 tasks, easy / medium / hard, on unseen test
sites, plus a chosen set of MiniWoB++ tasks. MiniWoB++ has its own
environment, so check early how your screen-based agent will connect.

Each task file: id, instruction, start page, success check, step limit.

Conditions:
  A. No verifier
  B. Pixel rule
  C. Your verifier
  D. Larger vision-language model

Keep everything else the same. Decide the retry rules before testing.
With no verifier there are no retries, so B, C and D measure verification
PLUS recovery. Say that clearly.

Repeat each task several times (suggested 3 to 5). Identical repeats of a
deterministic run add no evidence, so vary start conditions or injected
failures, and use the same ones for every condition.

Measure: task success rate, steps per task, retries, recovery rate, false
success rate, time per step, verifier time, RAM and GPU memory.

Statistics: report counts and confidence intervals. Because conditions use
the same tasks, use a paired comparison such as McNemar's test on one
result per task, or bootstrap over tasks. Ask your supervisor.

Error analysis: label every failed task by cause: planner, parser, OCR,
grounding, execution, timing, verifier, recovery.

Do not tune anything after looking at test results.

21. PROBLEMS YOU WILL PROBABLY MEET
-----------------------------------
Clicks land wrong       -> display scaling or window offset.
Screenshot too early    -> wait for stability, with a timeout.
Screen never stable     -> animations; ignore tiny changes, use timeout.
Parser misses small items -> larger input size or tiling.
OCR errors              -> upscale crops; allow fuzzy matching.
Verifier scores ~100%   -> suspect leakage or an easy shortcut.
Good on val, bad on test -> overfitting to your page styles; add variety.
Out of memory           -> smaller batch and images; use Colab/Kaggle.
Colab disconnects       -> save checkpoints often.

24. OPTIONAL STRETCH GOAL: VOICE COMMANDS
-----------------------------------------
STATUS: optional. Not in the approved proposal. Ask your supervisor first.
Start only after the main agent, verifier and experiment pipeline work
(after M9). Leave enough time for the final experiments (M11). The core
project must be complete without it.

How it fits (only the input changes):
  Speak -> speech-to-text -> check/edit the text -> Start -> planner
  -> same agent
The parser, grounding model and verifier do not change.

Tools (check versions and licences):
  Speech-to-text: a pretrained local model, such as faster-whisper
                  (small model) or Vosk
  Recording:      sounddevice

Suggested files:
  agent/voice/recorder.py       record from the microphone
  agent/voice/transcriber.py    audio -> text
  ui/app.py                     microphone button

Interface:
  - Press the microphone button to start, press again to stop.
  - Set a maximum recording length.
  - Put the recognised text in the instruction box so it can be edited.
  - Never run it automatically. The user must click Start.
  - Show clear messages: no microphone, nothing heard, recognition failed.
  - Typing must always work.
  - Keep the keyboard stop key. Do not rely on voice to stop the agent.

Risks:
  - Accents and noise cause errors, especially in usernames, passwords,
    email addresses and web addresses. Let users type or correct them.
  - Do not speak real passwords. Use fake accounts only.
  - Extra memory and processing load. Measure it, and consider whether the
    speech model should be unloaded before the agent runs.

Privacy:
  - Process audio on the laptop.
  - Do not save recordings by default; delete temporary audio files.
  - After downloading the model, check that it works offline.

Research:
  - A pretrained speech model adds an ML feature, but it is not your own
    training work or main contribution. The verifier stays the focus.
  - Run all main experiments with TYPED instructions.
  - If you evaluate voice, do it separately: word error rate, share of
    commands recognised correctly, and processing time.
  - Check that your ethics approval covers recording participants' voices
    before any voice user test.

Tests:
  [ ] Clear speech in a quiet room
  [ ] Background noise
  [ ] Silence
  [ ] No microphone or permission blocked
  [ ] Wrong recognition can be edited
  [ ] Nothing runs without clicking Start
  [ ] Works offline
