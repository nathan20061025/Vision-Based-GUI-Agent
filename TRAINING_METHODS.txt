TWO WAYS TO TRAIN A MODEL: FINE-TUNING AND FROM SCRATCH
=======================================================
Written 2026-11-26.

The text reader (RapidOCR) uses pretrained models, unchanged.


1. BASIC WORDS
--------------
Machine learning (ML)  A computer learns patterns from data.
Weights                The numbers a model learns during training.
Pretrained model       A model that already learned from other data.
Training from scratch  Start with new (usually random) weights.
Fine-tuning            Start with pretrained weights and train further on
                       your own data.

BOTH ARE ML TRAINING. Using a pretrained model without training it is not.
Changing settings in simple code (like the picture-change rule) is not.

Simple comparison:
  From scratch = teaching someone to read, starting from the alphabet.
  Fine-tuning  = teaching someone who can already read to understand
                 medical forms.


2. COMPARISON (usual cases, not guarantees)
-------------------------------------------
                     From scratch         Fine-tuning
Starting point       Usually random       Pretrained weights
Data needed          Usually much more    Usually less
Time and GPU         Usually more         Usually less
Risk of poor result  Usually higher,      Usually lower
                     with little data
Counts as training   Yes                  Yes


3. FINE-TUNING, STEP BY STEP
----------------------------
1. Choose a small pretrained model. Record its name, source and licence.
2. Prepare and check your labelled data.
3. Split it into training, validation and test groups.
4. Change the output to match your task (for example your item types).
5. Train. Often the early layers are kept fixed first, then some or all
   are trained with a small learning rate.
6. Use validation data to choose settings and when to stop.
7. Save the model, settings, data version and training log.

Good points: needs less data and computing power.
Weak points: the earlier training may be on very different pictures
(for example photographs, not screenshots), so it still must be tested.
The pretrained model's licence also applies to your use.


4. TRAINING FROM SCRATCH, STEP BY STEP
--------------------------------------
1. Choose a model design. Do NOT load pretrained weights.
2. Prepare and check a larger, varied labelled dataset.
3. Split it into training, validation and test groups.
4. First do a small trial to check the code and estimate the time. The
   trial does not show how good the final model will be.
5. Train for longer. Watch training and validation results.
6. Watch for overfitting: good on training data, poor on validation.
7. Save the model, settings, data version, random seed and training log.

Good points: you control the whole training and do not depend on earlier
weights.
Weak points: usually needs much more data and GPU time. Free cloud
notebooks have usage limits, so save checkpoints often.


5. HOW TO TELL WHICH ONE THE CODE DOES
--------------------------------------
Check the STARTING WEIGHTS. These are examples; check the current
documentation and your installed version before using them.

Ultralytics YOLO:
  Fine-tuning:
      model = YOLO("yolo11n.pt")       # pretrained weights
      model.train(data="screens.yaml")

  From scratch:
      model = YOLO("yolo11n.yaml")     # model design only
      model.train(data="screens.yaml", pretrained=False)

  screens.yaml describes your dataset and item types.

PyTorch / torchvision:
      from torchvision.models import resnet18, ResNet18_Weights
      model = resnet18(weights=ResNet18_Weights.DEFAULT)  # fine-tuning start
      model = resnet18(weights=None)                      # from scratch
  These lines only create the model. You still need to adjust the output
  and train it.

Warnings:
  - The file ending alone is not proof. A .pt file may be your own saved
    checkpoint, and a model built from .yaml can still load weights.
  - Read the training log for "weights loaded/transferred" messages.
  - You usually cannot tell the method from a finished model or its score.
    Write it down when you train.

7. HOW TO COMPARE THE TWO FAIRLY
--------------------------------
Keep the same: model design, data, splits, image size and scoring.
Give each method a fair amount of tuning, and report training time.
Use validation data to choose settings. Keep test data for the final
experiments. If possible, train each more than once with different random
seeds, because one run can be lucky.
Measures:
  Parser     precision, recall, mAP
  Grounding  top-1 and top-3 accuracy
  Verifier   precision, recall, F1, balanced accuracy, false success rate
All        speed on this computer, memory use, model size
Do not decide the winner before testing.

12. THE PLAN: DATA -> TRAIN -> CONNECT
--------------------------------------
For EACH of the three models:
  1. Get data: suitable public data, my own collected screens, or both.
     (No single ready-made dataset is needed for everything.)
  2. Label it and check the labels.
  3. Check licences and rules. Split into training, validation and test.
  4. Train or fine-tune with the training data.
  5. Check it with the validation data.
  6. Save the model, settings, data version and results.
  7. Connect it to the agent.
  8. Test the agent again: does the model help?

What data each model needs:
  Model              Data shows                       Likely source
  1 Screen parser    Screens with boxes and labels    Suitable public data
                     (buttons, text boxes, links...)  + my own screens
  2 Grounding        Instruction, screen and the      Suitable public data
                     correct item                     + my practice pages
  3 Verifier         Before and after pictures, the   Mainly my own examples,
                     action, success or failure       + public data if
                                                      suitable

Where each model connects (milestones):
  M6  Screen parser   Adds finding items on the screen. Works together with
                      the text reader.
  M7  Grounding       Replaces or improves agent/matching.py.
  M8  Verifier        Replaces the picture-change rule as the agent's check.

Agent flow when all three are connected:
  instruction -> planner -> screenshot -> screen parser + text reader
  -> grounding model -> action -> verifier -> continue or retry

KEEP the current simple methods (text matching and picture-change rule) so
they can be switched on and compared with the trained models. A new model
may not do better. Test it on the same validation examples and report the
real result. Keep test data for the final experiments (M11).

A model is not finished after one training run. It needs checked labels,
saved results, validation measures, a working connection to the agent and
a record of its mistakes and limits. It does not need perfect results.
